How the engine saves work

The goal is to spend less time on repeated arithmetic and memory traffic. These diagrams explain the CPU paths in the Rust engine.

The diagrams are small schematics. The 18.1× result measures the complete recorded f64 path. It does not measure each optimization separately.

Choose a computational method

Keep the neighborhood. Batch the arithmetic.

The engine reads consecutive variants in chunks. A ring buffer retains normalized columns that the next chunk still needs.

Let B be the new chunk and A be its retained neighbors. Two matrix products calculate their correlations:

  • BᵀB compares variants inside the new chunk.
  • AᵀB compares retained neighbors with new variants. The engine adds each cross-chunk pair to both LD scores.

The faer matrix kernels handle these blocks and use multiple CPU threads on native builds. Contiguous columns help the CPU reuse cached data.

Scratch matrices also survive between chunks. Full overwrites remove the need for a new allocation and zero fill at each product.

Window accuracy and work per chunk

The optional --snp-level-masking flag removes pairs outside each variant’s true window. The default preserves Python’s chunk-level window convention.

A chunk of c variants, w retained neighbors, and N samples needs approximately N × c × (w + c) arithmetic work. Local variant density affects w.

Move fewer bytes through the same calculation.

The --fast-f32 option keeps the same window and matrix algorithm. Genotype storage and matrix products use 32-bit floats instead of 64-bit floats.

A normalized value occupies four bytes instead of eight. Smaller genotype matrices reduce memory traffic and leave more room in the CPU cache.

A chunk contains 200 variants and 2,490 reference samples. Its genotype matrix needs {{ engine.methods.chunk_f64_mib }} MiB in f64 or {{ engine.methods.chunk_f32_mib }} MiB in f32.

These are calculated matrix sizes, not total process memory.

The engine keeps normalization statistics and corrected LD-score accumulation in f64. The f32 matrix products still change numerical precision.

The recorded f32 run took 66.3 seconds and differed by at most {{ engine.f32_error }} LD-score units. A smaller format does not guarantee the same accuracy for every dataset.

Normalization · Matrix kernels and parallel execution

Shorten the sample dimension before matrix work.

CountSketch assigns each sample to a bucket and a random sign. It sums signed, normalized values into d bucket rows instead of N sample rows.

The contiguous input path first calculates variant statistics from packed BED bytes. A second pass combines genotype decode, normalization, and the signed sum.

That fused pass writes directly into the sketch. It avoids a full decoded matrix in the hot path. Irregular variant extraction still uses a full-size fallback buffer.

The next matrix products use d rows. For 2,490 samples and d = 500, each dot product uses approximately five times fewer row terms.

This is a work estimate, not a measured fivefold speedup. The engine still reads the full input. The 18.1× benchmark above uses the exact f64 path.

What compression changes

The schematic uses one normalized synthetic variant and an illustrative hash assignment. Its six sample values enter three buckets, then rescale to squared norm N = 6.

Bucket collisions add noise. Larger d usually reduces that noise but increases matrix work. The engine rescales columns and applies a quadratic bias correction before the finite-sample correction.

These corrections do not remove all approximation error. LD-score error and downstream heritability error need separate comparisons against exact results.

The work per chunk becomes approximately N × c + d × c × (w + c). The full input scan remains proportional to N.
